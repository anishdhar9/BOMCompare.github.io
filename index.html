Item Master data quality

Checks the Item Master file by itself. No CAD BOM is needed. This catches manual edits in Vault or the ERP system that do not agree with other fields on the same row (for example, someone changes Quantity without updating Item Qty).

Material checks on 7-999-* purchased or catalog parts are excluded from the checks above, and from the counts below. Review them separately, in the Bought-Out Parts panel.

Long-Lead Parts (LLDBO) optional

Long-lead direct-bought-out parts are released to procurement early, ahead of the normal BOM release, to cover supplier lead times. Drop the "PNxxxx_LLDBO" file. Once the Item Master is also loaded, this check confirms that each part reached the released BOM. It also scans the Item Master itself for motor/actuator/seal/nozzle-like parts that look like they should be tracked here but aren't — this half runs as soon as the Item Master loads, even before an LLDBO file exists.

How it works & assumptions
  • Overview dashboard: a panel at the top shows one clickable tile per flag value (findings, quantity, material and revision mismatches, and Item Master quality issues). Each tile is color-coded, and tiles appear as data loads. Click a tile to jump straight to its details below. The dashboard and each section always show the exact source file or files being compared. This keeps two exports of the same BOM, with different Vault columns enabled, traceable.
  • One finding per part: the same part can legitimately be caught by several checks at once. For example, a part can be in the Item Master but not in CAD, and its Quantity and Item Qty can also disagree. The app does not report this as several problems. Instead, it ranks findings by severity: missing, then reference, then quantity, then revision, then material, then in-Item-Master-only, then the data-quality checks. Each part is owned by its most serious check. Every other mention renders muted, with an “also in: …” pointer. The Parts needing attention table at the top lists each part once, with all of its issues.
  • Allied parts: the app rolls up related parts, instead of repeating them. A missing assembly already absorbed its children. “In Item Master only” now does the same, over the Item Master's own Row Order hierarchy. A whole subassembly absent from the CAD BOM is one finding, not one finding per part (on a real export, 1033 rows became 11). Grouped children are not part of the actionable count. Click “show N grouped” to reveal them. The per-occurrence rows inside a quantity mismatch stay as they are. They show where the part is used, and are not duplicates.
  • Reviewing parts: tick the checkbox on a row in “Parts needing attention” once you've looked into it — it moves to the “Already reviewed” section right below, and the tile counts drop to match. This is remembered in your browser (not the exported file), so it's still there next time you open the app, even after reloading a fresh comparison. Click “Un-review” on a part in “Already reviewed” to bring it back.
  • Match key: the part number (the Vault item “Number” field), not case-sensitive.
  • CAD BOM sources: upload one file, or, for best results, two files together.
    • Vault multi-level BOM PDF (the web client's “Uses” report): the full CAD structure, including reference components. Hierarchy comes from indentation. This file carries no quantities, but it does carry Revision.
    • Inventor BOM export (.xlsx with Item, Part Number, QTY, and BOM Structure columns, and Material and Revision when those columns were included): the intended BOM, with quantities and virtual components. Reference components are excluded from it.
    • Vault Excel paste (a flat file listing): the full structure, with no hierarchy or quantities. The app infers grouping from the export's depth-first order, plus the Item Master hierarchy.
  • Missing from Item Master: part numbers found in the CAD BOM, but absent from the Item Master. This is the classic sign of a component set to BOM Reference in Inventor by mistake.
  • Reference assemblies: when a whole assembly is missing, its child parts are grouped under it and collapsed. A reference assembly's entire BOM is expected to be absent, so only the assembly itself needs action.
  • Reference items (needs two CAD sources): components in the full CAD structure (PDF or Vault paste) that are absent from the Inventor BOM export. This is the exact list of what is currently flagged BOM Reference in the model. Each entry is marked to show if it also reached the Item Master. Review this list to confirm every entry is intentional.
  • Quantity mismatches: the app compares the rolled-up total quantity per part (its own quantity, multiplied by parent assembly quantities, summed over all occurrences) between CAD and Item Master. This needs a source with a QTY column, which means the Inventor BOM export. The Vault PDF and flat paste carry no quantities.
  • Quantity cascades: the plain quantity check compares each part's total rolled-up quantity, so it cannot see WHERE a discrepancy starts — one bad assembly can surface as hundreds of separately-flagged descendants. When ALL of an assembly's mismatched direct children share one clean ratio (for example every child at exactly 2×), the app reports ONE finding for that assembly instead, with the ratio and child count. Every part in the affected subtree is grouped under that one finding, the same demotion "One finding per part" already applies elsewhere. Fix the one root-cause row and the rest of the subtree's findings resolve with it.
  • In Item Master only: items whose number never appears in the CAD BOM. These are stale entries, or entries added by hand, and are worth a review.
  • Item Master data quality: runs the moment the Item Master loads. No CAD BOM is required. This section runs nine checks on the file itself. Seven are listed here. The two release-blocking checks are described separately below, since each gets its own box. Every one of these checks skips the "END OF LINE" row, which is an ERP marker meaning the BOM is complete, not a part. Checks 5 and 6 also skip parts whose number does not start with "7-", which are procured at other company locations and cannot be corrected here.
    • The top-level row's Producer or Producer Number appears in its Description.
    • The "END OF LINE" entry has the organization's fixed part number and a whole-number Row Order.
    • The Quantity and Item Qty columns agree on every row. This catches a manual edit to one column that was not mirrored to the other. It only runs when the export carries both columns. A per-unit column, like "QTY per Unit", is never mistaken for Item Qty.
    • When the export includes an Entity Icon column, it reads "Normal" on every row.
    • Every row has a Title and a Description. Purchased or catalog parts, numbered "X-999-…", are only flagged when both fields are missing.
    • Every non-assembly, non-purchased row has a Material value.
    • The same part number, used at more than one BOM position, carries the same Revision everywhere.
    A check can pass on its own terms, but still turn amber ("OK, but see below") when a related CAD-vs-Item-Master comparison finds a real difference.
  • Sketch parts in the Item Master (7-333-…): release-blocking, with its own box. 7-333-… numbers are rough-sketch models. They may exist in CAD, but only ever as Reference. One reaching the released Item Master is a serious release error. The app reports every hit with its Row #, Row Order, immediate parent, and the full parent trail (for example, “ASSY-A (Top Assembly) › SUB-B (Sub Assembly)”), so you can trace exactly how the part got in. This check only flags parts in the Item Master. Finding them in CAD is expected, and is not reported.
  • Item state (obsolete or invalid revisions): release-blocking, with its own box. A released BOM should hold Certified items only. Obsolete, Invalid, and Phased Out states are errors, since the part was released against a dead revision. New is shown as an amber warning, not a failure, since genuine released exports do contain New rows. This check reads the Item Master's “State” column, which the app carefully separates from the neighboring “File Link State” and “State (Historical)” columns. Those two columns describe the CAD file link, not the item.
  • Material: CAD vs Item Master: active once a loaded CAD source actually carries material data (the flat Vault paste, or an Inventor BOM export that included the Material column). Vault's exported columns are user-configurable, so this varies by file. This check compares material for manufactured parts. It normalizes naming-convention differences (DIN vs AISI grade, spacing, abbreviation, and language), so it flags only genuine differences. A grade's L-suffix (304 vs 304L) stays significant. Purchased or catalog parts ("X-999-…") are excluded here too. They instead get a full, always-collapsed Bought-Out Parts reference panel (Item Master material and CAD material side by side, mismatches marked, never counted as findings).
  • Virtual parts: a BOM entry with no CAD file behind it. Every other check passes it, because the part itself is in both BOMs. Only its children are Item-Master-only, and they arrive as unexplained single rows. The app finds these exactly when the Inventor export includes the "Thumbnail" column (Inventor writes the literal text "(NULL)" when no CAD file exists, and an empty cell when one does), and every Item Master child of the part is absent from the CAD BOM. Without that column the app infers the same shape from structure, needing at least three orphaned children, and labels the result "suspected". A virtual part also groups its orphaned children underneath it in the "In Item Master only" tab, so the whole thing reads as one finding.
  • Description: CAD vs Item Master: compares the CAD Description against the Item Master Description for every shared part. Case and spacing are ignored, so "TANK - 300LTRS" matches "TANK - 300 LTRS". Punctuation and digits are not, so a changed dimension ("OD 539 X 4 THK." against "OD 539 X 3 THK.") or thread size ("G 1/4" against "G 1/8") is still reported. Purchased "X-999-" parts, parts procured at another company location (numbers not starting "7-"), the END OF LINE marker, and rows blank on either side are all excluded.
  • Revision: CAD vs Item Master: active once a loaded CAD source carries revision data, and the Item Master has a Revision column. Unlike material, there is no naming-convention ambiguity here, so the app compares revision values directly (trimmed, not case-sensitive). Any difference is a genuine finding, shown both in the main summary row's "revision mismatches" card, and in its own detail section.
  • Export file name: when the Item Master's top-level row carries the organization's SPN/PN project key (from its Producer or Producer Number columns, or parsed from the Description text), both the comparison export and the QC report include it in the file name.
  • Load from folder (Chrome and Edge only: a browser cannot read a typed path, so this feature uses the browser's own folder picker): click the button, and choose the PNxxxx project folder one time. The app then finds the "Autodesk Vault…" PDF, the "EBOM_…" Item Master export, an "INVENTOR_BOM_…" export (an optional second CAD source), and a "PNxxxx_LLDBO" file, if present. It loads every file it finds, runs the comparisons, and writes the result workbook straight back into that folder. There is no download step. If a required file is missing, or the folder has more than one candidate file, the app leaves that side empty for you to drop in manually. The normal upload boxes always work as a fallback.
  • Long-Lead Parts (LLDBO): optional, checked once both this file and the Item Master are loaded. Long-lead direct-bought-out parts are released to procurement ahead of the normal BOM release, to cover supplier lead times. This check flags any long-lead part number that never reached the Item Master (the early release was not captured, so the part may quietly never get ordered through the normal channel). It also flags any part whose long-lead quantity (summed if the same part appears on more than one line) does not match the Item Master's rolled-up total. If the LLDBO document's own SPN/PN project key does not match the loaded Item Master's key, a warning flags the likely mismatched files, before anything else is reported. Rows not yet assigned a part number are counted separately, and are not treated as findings.
  • LLDBO candidates (the opposite direction): runs from the Item Master alone, no LLDBO file required. It looks for parts whose Title/Description mention a long-lead keyword (motor, actuator, seal, gasket, nozzle, and the German "dichtung"/"düse"). A keyword match on a purchased-part-numbered row ("X-999-…") is a high-confidence candidate; the same keyword on a normally-numbered row (often a bracket, cover, or assembly that merely mentions the word) goes in a separate "needs manual review" list instead, and never counts as a flagged finding on its own. Before an LLDBO file is loaded, every candidate is shown as an uncross-checked preview. Once one is loaded, candidates already tracked there drop out, and only the high-confidence tier left over — a long-lead part nobody added to tracking — counts toward "Parts needing attention".
